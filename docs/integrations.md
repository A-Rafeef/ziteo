# Provider integration contracts

This baseline contains application code and deployable database definitions. Live accounts, DNS, merchant activation, secrets, and real provider callbacks still need activation and verification. Unit tests use mocked provider responses; they do not certify a live provider account.

## Phone verification

Seller sign-in remains Google or email/password. Phone verification happens when a seller prepares their first publication. `POST /api/v1/verification/send` takes `{ "channel": "sms", "captchaToken": "..." }` and returns an application challenge ID. `POST /api/v1/verification/confirm` takes `{ "challengeId": "...", "code": "..." }`. `GET /api/v1/verification` reports current verification.

The server uses the saved store phone, never a phone supplied with the confirmation request. PostgreSQL owns five-minute expiry, a five-attempt limit, a sixty-second resend delay, and an hourly send cap. Provider session IDs and verification writes remain server-only. Changing the store phone invalidates its publish eligibility.

The implemented 2Factor legacy SMS contract uses `POST /API/V1/{key}/SMS/{phone}/AUTOGEN/{optional-template}` and `/SMS/VERIFY/{session}/{code}`. Verification needs both `Status: Success` and `Details: OTP Matched`. Account/template approval and funded credentials are required. Provider URLs contain credentials, so do not include them in logs. See [2Factor SMS API](https://2factor.in/API/DOCS/SMS_OTP.html) and the [vendor's verification guide](https://dial2verify.com/corp/support-system/tkt/knowledgebase.php?article=19).

WhatsApp is deliberately gated with a clear unavailable response until the business/number and authentication template are approved and the account's complete send/verify contract is confirmed. The [current 2Factor overview](https://2factor.in/v4/index.html) advertises multichannel OTP, but its public example does not establish a complete verification response contract. No WhatsApp endpoint has been guessed.

Cloudflare validates `phone-verification` Turnstile tokens on the server, including expected action and allowed hostname. Tokens expire in five minutes and are single-use. Auth CAPTCHA tokens belong to Supabase's validation path; do not consume the same token twice. See [Turnstile validation](https://developers.cloudflare.com/turnstile/get-started/server-side-validation/).

## Premium subscriptions

Configure a Cashfree **periodic** plan in the matching merchant environment. `CASHFREE_PLAN_ID`, `CASHFREE_PLAN_AMOUNT` (major INR units), and `CASHFREE_PLAN_PERIOD_MONTHS` (1 or 12) must match that approved plan exactly. Do not invent a public selling price or reuse payment-gateway order APIs as subscription APIs. The default environment is sandbox.

`POST /api/v1/billing/subscribe` requires a signed-in seller, their saved store, and a verified store phone. It reserves the merchant subscription ID and UUID idempotency key before calling Cashfree. Timeouts reuse that reservation. Customer details are snapshotted, so retries retain the same body. The response contains `subscriptionId`, `sessionId`, and `mode`. Open Cashfree's SDK with `cashfree.subscriptionsCheckout({ subsSessionId: sessionId, redirectTarget: '_self' })`. An active existing mandate returns its status without opening another subscription.

The server sends `POST /pg/subscriptions` with `x-client-id`, `x-client-secret`, `x-api-version` (pinned to `2026-01-01`), and `x-idempotency-key`. It uses `sandbox.cashfree.com` or `api.cashfree.com` according to `CASHFREE_ENV`. See [Create Subscription API](https://www.cashfree.com/docs/api-reference/payments/latest/subscription/create-subscription) and [hosted subscription checkout](https://www.cashfree.com/docs/payments/subscription/hosted-checkout).

Configure the matching Cashfree subscription webhook as `https://YOUR_APP/api/webhooks/cashfree`, using the same API version. `CASHFREE_CLIENT_SECRET` verifies Base64 HMAC-SHA256 over the exact timestamp followed by raw body; malformed signatures and timestamps outside five minutes are rejected. A failed database transaction returns 503 for retry. See [subscription signature verification](https://www.cashfree.com/docs/payments/subscription/webhook-signature).

An `ACTIVE` mandate or successful `AUTH` payment does **not** establish paid Premium access. The database accepts only known-subscription `SUBSCRIPTION_PAYMENT_SUCCESS` events with `payment_type: CHARGE`, `payment_status: SUCCESS`, matching amount/currency, and a valid schedule date. Each provider payment contributes its own calendar billing period; unique payment IDs prevent duplicate extensions. Lifecycle state uses provider event time. Distinct successful refund IDs accumulate against their provider payment ID, even if a refund arrives before the charge. Only cumulative refunds covering the full payment remove that paid period; partial refunds preserve it. See [subscription event layouts](https://www.cashfree.com/docs/payments/subscription/webhooks).

`GET /api/v1/billing/status` returns paid-until, Premium status, environment, and the latest mandate status. Sandbox and production payments are isolated. Future paid feature enforcement must query production paid periods on the server, with `period_start <= now() < period_end` and `refunded = false`; frontend flags are not authorization. Cancellation does not erase an already-paid period. Cashfree handles periodic collection; this baseline creates no charging cron job.

Go-live checks: merchant KYC and subscriptions activated; approved price/cadence; public domain and return URL approved; sandbox auth/charge/failure/cancel/refund tested; duplicate and reordered webhooks tested against PostgreSQL; reconciliation and customer cancellation/refund policy established; production keys and webhook version configured. The application does not automatically charge a seller merely by logging in.

## Storage, email, analytics, monitoring

The implemented baseline uploads through the authenticated Next API into a private R2 bucket and serves images only after owner/public-reference authorization. It does not issue browser presigned uploads or require browser bucket CORS. If direct uploads are added later, R2 presigned URLs use the account S3 hostname and require explicit CORS. Private originals must remain inaccessible through public bucket domains. Cloudflare Images transformations can optimize an R2 original through `https://ZONE/cdn-cgi/image/width=...,quality=...,format=auto/ORIGINAL_URL` after enabling transformations and allowlisting source origins. No extra image-copy service is necessary. See [R2 presigned URLs](https://developers.cloudflare.com/r2/api/s3/presigned-urls/), [CORS](https://developers.cloudflare.com/r2/buckets/cors/), and [Images transformations](https://developers.cloudflare.com/images/optimization/transformations/overview/).

Resend application email uses its API. Supabase confirmation/reset email additionally requires custom SMTP: host `smtp.resend.com`, port 465 with TLS or 587 with STARTTLS, user `resend`, and API key as password, with a verified sender/domain. App environment variables alone do not configure Supabase Auth SMTP. Use stable email idempotency keys for retryable events; the API retains them for 24 hours. See [Resend SMTP](https://resend.com/docs/send-with-smtp), [Send Email API](https://resend.com/docs/api-reference/emails/send-email), and [Supabase SMTP](https://supabase.com/docs/guides/auth/auth-smtp).

PostHog's project token and ingestion host are browser configuration. Use stable Supabase user IDs for identity, reset on logout, and avoid email/phone in explicit event properties. Mask input values and page text for replay; enable replay only under the configured product/privacy choice. Feature flags do not grant paid access. See [Next.js SDK setup](https://posthog.com/docs/libraries/next-js) and [replay privacy controls](https://posthog.com/docs/session-replay/privacy).

Better Stack logs use a **source-specific ingestion host** and bearer source token, never a hardcoded legacy host. Send structured server logs without raw auth, phone, email, bank, or webhook data. Monitor the deployed health URL and alert on failures; alert destinations need account configuration. See [HTTP log ingestion](https://betterstack.com/docs/logs/ingesting-data/http/logs/) and [uptime monitor API](https://betterstack.com/docs/uptime/api/create-a-new-monitor/).
