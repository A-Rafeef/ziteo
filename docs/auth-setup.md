# Seller authentication

Ziteo uses Supabase Auth for Google and email/password. `owner()` validates the caller with `getUser()`. Browser requests use SSR cookies and `/api/v1` callers may use `Authorization: Bearer <Supabase access token>`. An invalid bearer token never falls back to a browser cookie. User metadata supplies display names only; store ownership always uses the verified user ID and database RLS.

1. Configure `NEXT_PUBLIC_SUPABASE_URL`, `NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY`, and the exact HTTPS `NEXT_PUBLIC_APP_URL` for each deployed environment. Never expose a Supabase secret/service-role key to the browser. Add only trusted application origins to Supabase's redirect allowlist, including `/auth/callback` and `/auth/callback?next=/auth/reset`.
2. Enable email/password and email confirmation. Require passwords of at least 12 characters in Supabase Auth settings too, so direct SDK calls have the same protection as the web form. Configure Resend SMTP in Supabase: verified sender domain, host `smtp.resend.com`, port 465 with SSL or 587 with STARTTLS, username `resend`, password the Resend API key. Verify delivery before launch; the default Supabase email sender is unsuitable for general production onboarding.
3. Create Google OAuth credentials for the actual business/project. Set Google's authorized redirect URI to `https://<supabase-ref>.supabase.co/auth/v1/callback`. Add these credentials under Supabase Auth → Google. Google sends users through Supabase, which then sends them to Ziteo's `/auth/callback` PKCE exchange.
4. Create a Cloudflare Turnstile widget with the application domains. Set `NEXT_PUBLIC_TURNSTILE_SITE_KEY` in the app. In Supabase Auth → Bot and Abuse Protection, enable CAPTCHA, select Turnstile, and save the widget's secret. Supabase performs the validation for sign-in, signup and reset; do not also call Siteverify with the same token. Production web authentication is unavailable without the sitekey. Direct Supabase auth endpoints are protected only after CAPTCHA is enabled in Supabase itself.
5. For cross-device email confirmation, set the confirmation email link to `{{ .SiteURL }}/auth/confirm?token_hash={{ .TokenHash }}&type=signup`. Set recovery emails to `{{ .SiteURL }}/auth/confirm?token_hash={{ .TokenHash }}&type=recovery`. Set `SiteURL` to the exact app origin. The `/auth/confirm` handler accepts only signup, email and recovery types. The normal PKCE `/auth/callback` flow also works when opened in the same browser that began the request.
6. Verify signup, confirmation, Google login, email/password login, password reset, invalid/expired links and sign-out against the staging project. Automated local browser checks cover the unauthenticated boundary and CSRF failures; they do not establish provider delivery or OAuth configuration.

Cookie mutations require the configured application's Origin. Sign-out accepts POST only. Auth callbacks use the configured canonical origin; neither forwarded host headers nor arbitrary return URLs control redirects. Responses with auth cookies must never be cached by a CDN.

Phone verification is separate from login. Sellers verify the current store contact number near first publish through the 2Factor verification endpoints. The workspace exposes the database-computed `phoneVerified` flag; browser-supplied values are never authoritative. Changing the contact number requires a new verification. WhatsApp delivery requires the provider's approved template/account setup and is not silently substituted for SMS.

Official implementation references: [Supabase SSR](https://supabase.com/docs/guides/auth/server-side/creating-a-client), [password authentication](https://supabase.com/docs/guides/auth/passwords), [CAPTCHA](https://supabase.com/docs/guides/auth/auth-captcha), [Google OAuth](https://supabase.com/docs/guides/auth/social-login/auth-google), [Resend SMTP](https://resend.com/docs/send-with-smtp).
